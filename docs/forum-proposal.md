# NanoCamp 论坛模块方案（讨论稿）

日期：2026-10-22。依据：当前本地源码 `adb0e0c`；功能、规模和排期均为建议，尚未开始实施。

## 1. 目标与定位

让活动现场、QQ群和微信群里的交流，能够沉淀为可搜索、可继续讨论的话题。论坛面向参与者，承接提问、经验分享、作品交流和寻找队友。

官网活动页发布已确认活动；作品页展示整理后的作品；社区页介绍参与方式；论坛承接日常讨论。用户的作品分享帖不自动成为官网精选作品，官方公告也不由普通用户直接发布。

首期假设：小规模、中文为主；公开浏览，现有邮箱账号登录并补全资料后参与；至少安排一位管理员处理举报。这里没有把假设当作现有运营事实。

## 2. 成熟产品参考与取舍

| 参考 | 已核实机制 | NanoCamp 采用方式 |
| --- | --- | --- |
| [Discourse](https://www.discourse.org/features) | 主题内平铺回复、引用上下文、草稿、通知、内容管理 | 主题页按时间阅读，回复保留上下文；优先保证发布与回复闭环 |
| [Flarum 标签](https://docs.flarum.org/extensions/tags/) | 主分类与辅助标签分工，可按分类限制权限 | 每帖一个主要分区，最多三个辅助标签；不搭多层空版块 |
| [GitHub Discussions](https://docs.github.com/en/discussions/managing-discussions-for-your-community/managing-categories-for-discussions) | 讨论、问答、公告使用不同分类格式，公告限制发起权限 | 问题可采纳答案，官方公告仅工作人员发起 |
| [Discourse 内容管理](https://meta.discourse.org/t/discourse-moderation-guide-part-3-managing-content/406266) | 举报进入审核队列，管理人员可处理话题与内容 | 上线即具备举报、隐藏、恢复、锁帖和审计记录 |
| [NodeBB](https://docs.nodebb.org/) | REST API 与插件扩展能力 | 作为独立论坛系统的备选，不能因其使用 Node 就视为可直接复用现有数据库和 Cookie |

上述是机制参考；以下布局、参数和范围是针对 NanoCamp 的设计建议，不是这些产品的默认行为。

## 3. 技术路线

| 路线 | 优点 | 成本与局限 | 适用情况 |
| --- | --- | --- | --- |
| 在现有 Node + MySQL 内新增论坛（建议） | 一个账号、一套导航、可完全保持现有风格；活动和作品可原生关联 | 发帖、审核、通知、权限与安全测试都需自行实现维护；总成本未必低于成熟系统 | 论坛规模小、首期功能克制、站内体验优先 |
| 独立部署 Discourse 并接入统一登录 | 论坛核心功能和管理工具成熟 | 新增独立部署、升级备份、登录桥接和主题适配；不能直接共享现有会话即完成登录 | 运营优先，期望尽快获得成熟论坛能力 |
| 独立部署 Flarum / NodeBB | 可以利用已有讨论功能和扩展机制 | 仍需验证登录接入、数据模型、插件维护与样式适配 | 团队已有相关部署经验 |

建议先采用原生小论坛，但在确认首期范围后再做最终选型。如果必须同时上线实时聊天、私信、复杂等级、多层版块和大量扩展，转向成熟论坛系统更合理，不建议逐项自研追平。

## 4. 分区与内容

初期只设四个分区：

| 分区 | 内容示例 | 特殊行为 |
| --- | --- | --- |
| 提问与交流 | 工具使用、学习问题、技术探讨 | 发帖时可选“问题”，作者或管理员可采纳一条回复 |
| 作品与实践 | Demo、开发过程、复盘、试用反馈 | 可关联现有作品页链接，不重复制作一套作品库 |
| 组队与招募 | 找队友、共创协作、活动志愿者 | 作者可标记“招募结束”，不等同于锁帖 |
| 社区事务 | 官方公告、社区建议、活动讨论 | 普通成员可提建议；只有管理员/版主可发公告 |

“活动”“AI”“设计”“前端”等作为辅助标签；初期由管理人员维护标签池，避免同义标签泛滥。每帖一个分区，0—3 个标签。分区和类型分开建模：分区表示内容归属，类型决定是否支持答案采纳、结束招募等行为。

## 5. 页面与布局

### 全站接入

- 导航新增“论坛”，保留“社区”的介绍职责；检查桌面断点和手机菜单，避免强塞导致导航溢出。
- 右上角沿用现有登录状态入口。个人中心增加“我的话题”“我的回复”“我的收藏”“消息”入口。
- 话题作者使用昵称和站内作者页链接，不展示邮箱；首期可用现有品牌图形/昵称首字作为默认头像，头像上传后置。

### 论坛首页 `/forum/`

```text
现有全站导航                                      登录状态
论坛标题                                         发起讨论
┌ 分区导航 ┐ ┌ 最新 / 未回复 / 已解决；搜索话题 ──────────┐
│ 全部话题 │ │ 标题、分区/标签                          │
│ 提问交流 │ │ 作者 · 更新时间              回复数       │
│ 作品实践 │ │ ─────────────────────────────────────── │
│ 组队招募 │ │ 标题、分区/标签                          │
│ 社区事务 │ │ 作者 · 更新时间              回复数       │
└─────────┘ └ 下一页/上一页；筛选条件保留在 URL ─────────┘
```

以标题为主的列表，不为每条话题放大封面。桌面采用轻侧栏 + 主列表，移动端改为顶部可横滑分区和单列话题。没有内容的筛选展示真实空态，不填充虚假热度。

首期默认按最近公开回复时间排序，置顶限少量官方帖；同时提供最新发布、未回复和已解决筛选。编辑、点赞、隐藏内容不顶帖。暂不提供难以解释和容易刷量的“综合热度”。每页 20 个话题，采用明确分页便于返回定位。

### 话题详情 `/forum/topics/:id/`

- 标题、分类、作者、发布时间和编辑状态。
- 主帖独立成段，回复单列按时间顺序展示，每页 30 条。
- 回复按钮在登录前后保持可发现；未登录进入登录页，保留原始话题地址。
- “回复某条”记录目标回复并显示引用入口，讨论仍然平铺，不做无限楼中楼。
- 问题帖的采纳答案显示独立摘要和定位链接，原回复不复制成两份；“已解决”不自动锁帖。
- 话题菜单包含作者编辑、删除申请/撤回，以及管理操作；举报始终指向具体主帖或回复。
- 回复使用稳定锚点，例如 `/forum/topics/123/?page=2#reply-456`，分页下通知链接仍能准确定位。

### 发布与编辑 `/forum/new/`、`/forum/topics/:id/edit/`

- 标题 → 分区/类型 → 正文 → 标签 → 预览 → 发布，移动端编辑与预览切换。
- Markdown 支持段落、列表、引用、代码块和普通链接，禁用原始 HTML；首期暂不上传图片、附件，也不自动抓取链接预览。
- 本机草稿按用户 ID 隔离，登录后可恢复；不把 Cookie、密码、验证码存进草稿，退出后清理该账号草稿。说明“仅保存在当前浏览器”，避免误认为跨设备同步。
- 首次进入发帖时要求补全现有密码与昵称；无权限、数据库故障和会话过期分别提示，失败保留编辑内容。

### 个人与管理

- `/forum/me/`：我的话题、回复、收藏及各自状态，仅本人可查看。
- `/forum/notifications/`：回复我的话题、回复我的回复、被采纳、管理处理结果；可标记已读。
- `/forum/users/:id/`：仅公开昵称、可选简介及公开贡献；不复用私有 `/profile/` 页面作为公开主页。
- `/forum/moderation/`：管理角色专用举报队列，显示上下文、处理理由和操作记录；权限在服务端校验。

### 与全站视觉一致

复用 NanoDisplay 标题、浅紫纸色、蓝绿强调和现有导航；纸张元素用于发帖入口、分区和空态，正文使用稳定、清晰的阅读版心。避免把每个帖子做成扇形卡片。标题、正文、代码、时间和操作形成固定层级。动效只用于菜单、编辑器展开和发布反馈，并遵循减少动态效果设置。

## 6. 首期范围与交互规则

首期完整上线必须包含：分类浏览与搜索、发布/编辑主帖、回复、采纳答案/结束招募、点赞与收藏、个人内容入口、站内通知、举报和基础管理。为避免范围过大，先分批内部验收，再开放运营。

暂缓：图片/附件上传、私信、实时聊天、粉丝关系、积分等级、勋章、AI 总结、付费内容、邮件订阅、复杂推荐。以后做图片时必须补齐对象存储、独立上传接口、类型/尺寸校验和访问控制，不能把大文件塞进当前 JSON 请求体。

| 动作 | 建议规则 |
| --- | --- |
| 主帖 | 标题 4—80 字，正文 10—15,000 字；统一以 Unicode 字符计数，另保留字节上限 |
| 回复 | 1—3,000 字；同一话题内可回复指定楼层；不能引用其他话题的回复作为父级 |
| 编辑 | 作者可修改自己的可见内容，保存版本号与修订记录；并发修改返回冲突，不静默覆盖 |
| 删除 | 无回复主帖可撤回；已有回复主帖允许撤回作者正文，保留讨论骨架，整帖下架由管理人员处理 |
| 回复撤回 | 替换为撤回占位，保留引用关系；管理隐藏内容不向普通用户返回原文 |
| 点赞/收藏 | 登录才可操作，唯一约束防重复；点赞主帖和回复，收藏仅话题；两者均不顶帖 |
| 发布防重复 | 客户端每次发布携带幂等键，用户+操作+键唯一，超时重试不重复插入 |
| 访问 | 游客只读公开内容；未补全资料成员先补全；禁言成员可阅读，不可写入 |
| 初期限流 | 建议新账号每小时 3 个主帖、20 条回复，重复提交需间隔；参数可配置，真实运营后调整 |
| 新人审核 | 默认已验证邮箱和完整资料可发布；若有审核人力，再启用首帖预审，不能产生无人处理的等待队列 |
| 举报 | 每人每目标只能有一条未结举报，重复请求幂等；首期不按举报数量自动删帖 |
| 通知 | 站内通知为主；作者和明确回复对象分别通知，同一人合并，自我互动不通知；不通知所有围观者 |

## 7. 权限与管理状态

增加 `member / moderator / admin` 三种角色。角色不允许通过个人资料接口修改；初始管理员通过受控初始化脚本授予，以后授权记录审计。

| 能力 | 游客 | 普通成员 | 版主 | 管理员 |
| --- | --- | --- | --- | --- |
| 看公开话题、搜索 | 是 | 是 | 是 | 是 |
| 发帖、回复、点赞、收藏 | 否 | 资料完整且未禁言 | 是 | 是 |
| 改自己的内容 | 否 | 按内容状态规则 | 是 | 是 |
| 处理举报、隐藏/恢复、锁帖、改分类 | 否 | 否 | 是 | 是 |
| 置顶公告 | 否 | 否 | 是 | 是 |
| 设置角色、管理分区、封禁账号 | 否 | 否 | 否 | 是 |

内容可见状态为 `published / pending / hidden / withdrawn`，讨论关闭独立使用 `locked_at`。问答 `accepted_reply_id` 和招募 `resolved_at` 是业务状态，不混入可见状态。隐蔽内容在列表、详情、搜索、通知摘要、作者页中执行相同过滤。待审核内容只对作者和管理者可见；普通访客访问返回 404，避免泄露标题和存在性。

审核动作必须有操作人、时间、目标、理由和前后状态；普通成员不能通过猜测 ID 查看举报人、审核队列或被隐藏正文。锁帖和权限撤销须在写入事务内再次核对，避免通过并发绕过。

## 8. 与当前代码的具体衔接

已核实可以复用：现有 `users`、`sessions`、邮箱验证、scrypt 密码、`readSession`、双提交 CSRF、个人资料完整度检查、参数化 MySQL 查询、全站模板与样式。

已核实需要调整：

1. `backend/app.mjs` 的公共内容采用进程内 `renderOnce` 缓存。论坛页需要独立的请求期渲染入口，不能放进这个永久缓存，避免发帖后不更新或私有内容串用户。
2. `backend/api.mjs` 当前使用固定路由白名单。新增论坛路由分发和统一鉴权，不能只做前端按钮判断。
3. `backend/db.mjs` 尚未提供业务事务封装。新增同一连接上的事务能力，主题、回复计数、通知和幂等记录等一起提交或回滚，禁止在事务中混用连接池全局查询。
4. `backend/main.mjs` 请求体上限为 64 KB。首期保持此上限并限制正文；后期图片上传独立流式处理，不全局调大。
5. `src/search.mjs` 生成现有站点的页面/FAQ/作品索引。论坛搜索应走独立数据库查询，不把每次发帖追加到静态索引；现有站内搜索提供“搜索论坛”入口，后续再统一展示结果。
6. 当前 `CREATE TABLE IF NOT EXISTS` 不会升级已有表。论坛需要版本化迁移记录，新增角色字段必须走显式迁移；本地、测试、生产依次验证。

建议新增文件：`backend/forum.mjs`（业务及权限）、`backend/forum-api.mjs`（接口适配）、`backend/forum-store.mjs`（查询与事务）、`src/forum.mjs`（页面）、`public/forum.css`、`public/forum.js`、独立迁移脚本与论坛测试。已有认证模块保持单一账号来源。

## 9. 数据设计草案

| 表/变更 | 核心内容与约束 |
| --- | --- |
| `users` 扩展 | `role`、`posting_suspended_until`、`banned_at`；角色字段不出现在普通可更新字段白名单中 |
| `forum_categories` | 名称、稳定 slug、顺序、可用类型、发帖权限 |
| `forum_topics` | 作者、分类、类型、标题、Markdown/纯文本、可见状态、版本、锁帖时间、采纳回复、招募结束时间、公开回复数、最新公开活动时间 |
| `forum_replies` | 话题、作者、可选目标回复、Markdown/纯文本、状态、版本、顺序号与时间；唯一 `(topic_id, sequence)` |
| `forum_tags` / `forum_topic_tags` | 标签池及话题关联，组合唯一，数量服务端限制 |
| `forum_topic_likes` / `forum_reply_likes` | 各自以目标 ID + 用户 ID 唯一，避免多态目标缺乏关系约束 |
| `forum_bookmarks` | 用户 ID + 话题 ID 唯一 |
| `forum_notifications` | 收件人、事件唯一键、话题/回复 ID、事件类型、已读时间；打开前再次验证目标可见性 |
| `forum_reports` | 举报人、目标、理由、处理人、状态；目标使用话题/回复可空外键并约束二选一，服务端补校验 |
| `forum_moderation_logs` | 操作人、目标、动作、理由、前后状态、时间；禁止普通成员读取 |
| `forum_revisions` | 内容目标、历史版本、编辑者、时间，仅作者和管理者按权限读取，隐藏正文不从版本接口泄露 |
| `forum_write_requests` | 用户、操作、幂等键、结果 ID 和过期时间，组合唯一 |
| `schema_migrations` | 已执行版本与时间，已应用迁移不自动重复执行 |

计数仅统计公开内容，隐藏/恢复/撤回要同步更新。采纳答案必须属于同一主题并处于公开状态；被隐藏或撤回时撤销采纳。引用回复必须属于同一主题。用户被删除/匿名化的策略在实施前确定，不采用级联删除整段社区历史。

首期不存浏览量，避免刷新刷量和额外写放大。列表索引围绕 `(status, category_id, last_activity_at, id)`；回复围绕 `(topic_id, status, sequence)`；通知围绕 `(user_id, read_at, id)`。SQL 必须参数化；排序字段和分类筛选使用白名单。

搜索小规模先采用受限长度的参数化 LIKE 查询，转义通配符、分页并设结果窗口上限；中文全文检索在真实数据压测后再决定 MySQL ngram 或独立搜索服务。不能把普通英文分词全文索引当作中文搜索已解决。

## 10. 接口与一致性约定

| 接口 | 用途 |
| --- | --- |
| `GET /api/forum/topics` | 分区、标签、关键词、排序和分页的公开列表 |
| `GET /api/forum/topics/:id` | 主帖与当前页回复，按查看者权限过滤 |
| `POST /api/forum/topics` | 创建话题，要求会话、完整资料、CSRF 和幂等键 |
| `PATCH /api/forum/topics/:id` | 作者编辑，携带预期版本，冲突返回 409 |
| `POST /api/forum/topics/:id/replies` | 回复，同时事务更新公开活动时间、计数与通知 |
| `PATCH /api/forum/replies/:id` | 编辑自己的回复，执行版本校验 |
| `POST /api/forum/topics/:id/withdraw` | 撤回作者内容，保留必要占位 |
| `POST /api/forum/replies/:id/withdraw` | 撤回回复 |
| `POST /api/forum/topics/:id/answer` | 设置/撤销采纳，同主题校验与作者/管理权限 |
| `POST /api/forum/topics/:id/recruitment` | 结束/重开招募，只有招募帖有效 |
| `POST /api/forum/topics/:id/like`、`.../bookmark` | 请求显式携带目标 `enabled`，重复请求结果稳定 |
| `POST /api/forum/replies/:id/like` | 回复点赞/取消 |
| `GET /api/forum/me` | 本人话题、回复、收藏，禁止共享缓存 |
| `GET /api/forum/notifications` | 本人消息及未读数 |
| `POST /api/forum/notifications/read` | 标记本人指定通知已读 |
| `POST /api/forum/reports` | 举报内容 |
| `GET /api/forum/moderation/reports` | 有权限的管理者读取举报队列 |
| `POST /api/forum/moderation/actions` | 带预期版本的隐藏、恢复、锁定、置顶等处理，并写审计 |

所有写接口复用同源检查与 CSRF；私有读接口同样校验会话，输出 `Cache-Control: no-store`。内容变更在数据库事务中完成，发布接口返回服务器最终状态。初期不做乐观增加回复数，避免失败后界面出现不存在的内容。

错误明确区分：401 未登录、403 无权限/CSRF、404 内容不可见、409 版本或业务冲突、413 请求过大、422 输入错误、429 限流、503 依赖不可用。会话过期保留草稿，登录后回原始路径；数据库错误不能展示成空论坛。

Markdown 渲染引入经过评估的解析/清洗库，禁 HTML 和危险 URL，避免自行用正则拼装。外链使用安全协议、适当的 `rel`；首期禁自动远程图片和链接抓取，避免额外隐私、失效与服务端抓取风险。

消息先随登录后页面加载请求未读数，论坛可见时每 60 秒刷新；后台页暂停请求，不上 WebSocket。回复通知、计数与内容写入一起事务提交，不依赖外部邮件服务可用性。

## 11. 实施与验收

### 阶段 A：基础闭环（内部体验）

迁移、角色、公开列表/详情、登录回跳、发帖、回复、编辑与撤回、Markdown 安全渲染、幂等及限流。此时仅内部邀请测试。

### 阶段 B：可运营首版

分区标签、问题采纳/招募结束、点赞收藏、消息、个人贡献入口、搜索、举报与管理审计。完成可访问性和移动端验收后开放。管理工具不得排到公开上线之后。

### 阶段 C：根据实际使用扩展

图片、云端草稿、跨站搜索融合、邮件订阅、阅读进度。只有确有需求再评估私信、实时推送、复杂声望体系；运营规则与存储预算另行确认。

必须通过的验收场景：

1. 游客查看话题 → 点击回复 → 登录/补全 → 回到原始讨论地址继续操作。
2. 两个账号分别发帖、回复、采纳和收藏，互相不可修改内容或查看私有信息。
3. 网络超时重发只产生一个帖子/回复；并发编辑返回冲突，锁帖与禁言不能被并发绕过。
4. 回复排序、分页和通知锚点稳定；隐藏回复不出现在公开计数、搜索、通知摘要或历史接口。
5. 评论含 HTML、脚本、危险链接及代码片段时安全显示，Markdown 预览和最终渲染一致。
6. 登录状态、草稿和消息不串账号；退出、会话过期和无 JS 时有清晰的下一步。
7. 举报 → 管理员处理 → 内容隐藏 → 作者收到处理结果；恢复可追溯，普通成员无法调用管理接口。
8. 停库时明确提示服务不可用；恢复后不丢内容，事务失败不留下半条回复和假通知。
9. 桌面与 360/390px 手机验证标题换行、编辑器、键盘焦点、菜单、代码块滚动、减少动效。
10. 真实 MySQL 跑业务集成测试；新增浏览器端到端测试覆盖“发帖—回复—采纳—举报—隐藏”。上线前验证数据库备份可恢复。

上线观察完成发布的比例、首次回复耗时、未回复主题数量、发帖失败率和举报处理耗时，不预设虚假用户量/热度指标。首期可以通过运营记录和基础应用日志观察，不先引入整套分析平台。

## 12. 实施前需要最终确认的选择

- 是否接受首期纯文本/Markdown、链接和代码块，图片放下一阶段？本方案默认接受。
- 是否保留“社区介绍”和“论坛”两个入口？本方案默认保留。
- 谁担任首位管理员、能否持续处理举报？默认至少一人，授权按用户 ID 进行，不从邮箱域名自动推断身份。
- 内容是否全部公开？本方案默认公开；私密小组和活动内讨论需要另一套可见性设计。
- 是否选择原生模块路线？本方案倾向原生小论坛；若首期范围显著扩大，重新评估独立 Discourse。

以上默认选择足够继续做论坛首页、详情页、编辑器三张设计稿；开发前再将确认结果固化为迁移、接口和验收清单。当前文档不代表功能已实现，也未更改网站或发布线上内容。
