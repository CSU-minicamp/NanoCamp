## 一、业务线总览

| 业务线 | 起点与操作 | 系统结果 | 用户回访入口/完成标准 |
| --- | --- | --- | --- |
| 1. 身份与参与资格 | 游客阅读；互动时登录并补全现有资料 | 会话可用、恢复原页面与操作目标 | 右上角个人中心；登录失败不丢输入，不自动替用户发布 |
| 2. 内容发现 | 全部/分类/关注列表、关键词搜索、分页、排序 | 找到可公开阅读的话题，条件保留在 URL | 返回列表恢复位置；隐藏内容不出现在结果中 |
| 3. 内容创作 | 发帖、预览、草稿、发布、编辑、撤回 | 内容与作者持久化、可分享稳定地址 | 我的帖子；失败保留输入，重复提交只创建一次 |
| 4. 讨论交流 | 回复主帖、回复某条、编辑/撤回回复 | 回复可定位，更新公开回复数和活动时间 | 我的回复、回复消息；收件人点击定位具体楼层 |
| 5. 用户关注 | 看到作者→查看公开主页→关注/取消关注 | 持久化用户关注关系，关注列表提供作者新主题 | 关注动态、关注/粉丝列表；刷新后状态不丢 |
| 6. 内容投票 | 对主帖/回复点赞、踩、取消或改票 | 同用户同内容只有一个投票，数字与本人状态一致 | 重进页面还原投票；点赞收到站内提醒，踩不公开投票者 |
| 7. 收藏 | 对主题收藏/取消收藏 | 形成本人私有收藏记录，不影响排序 | 我的收藏；内容隐藏后不泄露原文 |
| 8. 举报处理 | 对主帖/回复选择原因、提交说明 | 形成可追踪工单；运营受控处理并记录理由 | 我的举报、处理结果消息；不能止于“提交成功” |
| 9. 站内消息 | 回复、被关注、收到点赞、举报结案或内容处理 | 消息产生、合并去重、未读与已读 | 消息列表→对应内容/用户/处理结果；目标不可见时解释状态 |
| 10. 个人内容与关系 | 从右上角进入个人中心 | 汇总帖子、回复、收藏、关注、粉丝、举报及消息 | 本人私有内容与公开作者主页严格区分 |

“最小”指每条保留的业务都能走完，缩减的是实现形式与次要变体，不删掉互动后的去向。

## 二、首期范围

### 必须形成同一个公开版本

公开浏览、三个分类、搜索与分页；现有登录衔接；发帖与回复、草稿、预览、编辑撤回；关注作者和关注动态；主帖/回复的赞踩；收藏主题；站内消息；举报提交、受控处理、结果回执；公开作者主页及个人中心各入口。

### 暂缓

网页管理后台、私信、即时聊天、图片/附件/头像上传、邮件推送、积分勋章、付费、AI 推荐、问答采纳、多级楼中楼、自定义标签、话题订阅。关注只表示“关注用户”；收藏只表示“保存主题”。不将三种概念做成一个含糊的关注按钮。

三个分类保持为提问交流、作品实践、组队招募。问答采纳、招募结束等类型状态后续增加，首期所有分类共用同一套讨论规则。

## 三、逐条闭环规则

### 1. 身份

沿用现有邮箱登录、用户 ID、昵称、会话和资料检查。游客可读，写操作要求登录、资料完整、未被禁言。登录回跳保留目标与编辑草稿，但恢复后由用户再次点击提交，不静默补发点赞或举报等操作。

用户 ID 是作者与关系主键，昵称变化不影响内容归属。公开主页不显示邮箱、举报历史或私有收藏。首次管理员/维护权限通过受控初始化授予，不能通过修改个人资料自助获得。

### 2. 发现与创作

首页默认最近公开回复，可切最新发布。搜索标题与正文，分类/关键词/排序/分页均写 URL。默认头像、标题、一行摘要、作者/分类/时间、回复数构成列表；不首期做热榜和浏览量。

发帖建议标题 4—80 字、正文 10—15,000 字；回复 1—3,000 字。正文允许 Markdown、代码、链接，禁止原始 HTML、远程图片及服务端链接抓取。使用维护中的解析清洗库，安全规则在预览和最终展示保持一致。

草稿保存于当前浏览器，按用户隔离，发布成功清除；退出清理对应草稿。字数限制之外仍执行当前 64KB 请求体限制。每次发布携带幂等键；超时重试返回原内容，不重复插入。编辑携带版本号，冲突时保留本地输入供用户重新合并。

作者可以撤回自己的主帖/回复；有他人回复时保留讨论骨架和撤回占位。撤回主题不再接收新回复。撤回内容不进入公开摘要和搜索；由运营隐藏的内容作者不能通过编辑绕过隐藏。

### 3. 回复

平铺按时间阅读，支持“回复某人”以及跳转到被回复的内容，不无限嵌套。被回复对象必须属于同一主题；引用对象撤回时保留对象信息，不展示撤回原文。

回复主帖通知楼主；明确回复某条时通知该回复作者，同时通知楼主；目标为同一个人时合并，自己给自己回复不发消息。发布后定位到新增回复，消息链接跨分页仍可找到具体楼层。

### 4. 关注用户

作者区域、公开主页提供“关注/已关注”。不能关注自己。关注后可从首页“关注”页签查看所关注用户的新主题，按发布时间排序，每个主题只出现一次。首期不将其每一次点赞、回复、收藏都扩散为动态。

动态读取当前关注关系，默认展示所关注作者现有的公开主题，不要求从关注时刻起才可见。取消关注立即从关注动态排除该作者；不删除既有互动。

关注/粉丝列表分页，公开账号关系，但不暴露邮箱。被封禁账号不能新增关系；相关公开内容按内容可见状态处理。关注成功给对方一条站内消息，同一人反复关注/取消不能刷出多条消息；取消关注不发送通知。

### 5. 点赞与踩

每个用户对每个主帖/回复的投票状态为 `none / up / down`，互斥：再次点击当前选项取消，点击另一选项直接切换，不出现同时赞和踩。请求使用明确目标状态，避免双击与重试导致多次翻转。

显示赞数、踩数以及本人的选中态；首期不做积分增减、踩到阈值自动隐藏、按票数自动降权或回复重排。不能对自己内容投票。作者看不到踩的人员列表，服务端也不提供该列表给普通用户；不向作者发送“被踩”提醒。投票者身份对维护人员仍可审计，不承诺绝对匿名。

点赞可产生聚合通知，例如某帖收到新的赞；取消点赞不产生通知，同人反复赞/取消不能刷提醒。通知摘要读取当前有效点赞结果，不在取消后继续显示过期的“某人赞了你”。投票失败恢复原状态并给出反馈。

踩表达内容评价，举报表达需要处理的违规/不当内容，两者互不替代。不因为踩多而自动生成举报，不因为举报多而直接认定违规。

### 6. 收藏

收藏只针对主题，形成本人私有列表。不通知作者，不把收藏关系公开，不顶帖。重复收藏幂等。内容撤回/隐藏时收藏仍可显示状态占位与取消入口，但不能泄露正文；恢复后可重新访问。

### 7. 举报与处理（不做网页管理页）

主帖和每条回复的“更多”菜单提供举报。理由建议：垃圾推广、人身攻击/骚扰、隐私泄露、违法或不当内容、其他；其他要求说明。首期不单独建立“举报用户”工单，针对具体行为的内容举报可关联被举报作者。

闭环：选择原因 → 提交并得到举报编号 → 我的举报显示待处理 → 运营查看上下文与记录 → 结案并填写理由 → 举报人收到结果 → 涉及内容处置时作者收到说明。举报人身份不暴露给被举报者，操作记录不对公众开放。

最小状态为 `open / reviewing / upheld / dismissed / withdrawn`；允许举报人撤回尚未开始处理的工单。相同举报人对相同目标只能有一条未结束工单；重复提交返回既有编号。结案后只在有新依据时允许重新提交并限流。内容被别人先撤回时仍需结案，不能一直挂在队列。

受控维护命令提供待处理列表、详情、认领、结案/隐藏/恢复及解除隐藏，必须记录处理人 ID、理由、前后状态与时间，校验操作权限及工单版本。数据库凭据放在部署环境，不提供给普通用户；不上线一个可以凭公开 HTTP 调用的“脚本接口”。通知与处理状态事务提交。

不按举报数自动下架，避免恶意围攻。至少有一名实际处理人是开放举报功能的前提；若无人处理，不能把“能提交举报”当作已完成公开运营闭环。当前是方案，不代表已安排运营人员或承诺处理时效。

### 8. 消息与个人中心

站内消息分“回复”“互动”“系统”，首期覆盖回复、关注、点赞聚合、举报结果、内容处理结果。明确回复消息定位楼层；点赞消息到主题或回复；关注消息到公开用户页；举报结果到本人举报详情。

踩、取消点赞、取消关注和收藏不发通知。消息有未读/已读，支持单条和全部已读。进入列表不自动读完所有消息；点击某条并取得对应结果后标记，目标撤回也给出状态页并可读。隐藏内容不通过消息摘要泄露，历史关注消息反映当前关系，不伪装为仍在关注。

页面可见时低频刷新未读数，首期不用 WebSocket 或真实邮件。个人中心私有页：我的帖子、我的回复、我的收藏、我的关注、我的粉丝、我的举报、消息；公开用户页只显示昵称、简介、公开帖子/回复及关注入口。

## 四、重新规划页面职责

### 论坛首页

顶部标题与“发起讨论”是主要发布入口。左侧分类与我的参与；主栏“全部/关注”页签、最近回复/最新发布、搜索、分页话题列表。右上角现有账号入口进入个人中心，增加独立的消息入口及未读数，避免将昵称点击变成含糊的复合功能。

### 帖子详情（纠正原型）

桌面布局：

```text
全站导航                              消息 / 个人中心
论坛 > 分类
┌──────── 当前讨论主栏 ─────────┐  ┌─ 作者栏 ───────┐
│ 标题、作者、时间              │  │ 默认头像、昵称 │
│ 正文                          │  │ 简介           │
│ 赞 / 踩 / 回复 / 收藏 / 更多   │  │ 关注/已关注    │
│                              │  │ 查看公开主页   │
│ 回复列表（赞/踩/回复/更多）    │  └───────────────┘
│ 回复编辑框、发布回复          │
└──────────────────────────────┘
```

详情右侧没有“发起讨论”，也没有招募广告或其他动作。作者看自己时显示“查看我的主页”，不显示自我关注。回列表使用面包屑。当前帖子内优先引导“参与回复”。举报放更多菜单，不和常用操作竞争。

窄屏把作者信息与关注放到主帖头部，不保留空的右栏。主帖与每条回复都要有各自的赞踩状态，不能在页面上只放一组不明确的投票按钮。主帖收藏按钮固定属于主题；不为每条回复增加收藏。

### 发帖/编辑页

标题、分类、Markdown 编辑/预览、本地草稿状态、发布/保存修改。发布讨论只出现在这里；详情页底部按钮为“发布回复”，不会创建新主题。

### 公开用户主页

昵称、简介、关注/粉丝数量及列表入口、关注按钮、公开帖子与回复。本人访问不显示关注自己，不公开邮箱、收藏、举报、收到的消息。

### 个人中心与消息

复用现有个人中心，增加论坛相关子页。我的举报能查看编号、状态和结论；消息页支持类别和已读操作。不存在“管理页”或普通成员可见的内容处置入口。

## 五、实现边界

继续复用 Node + MySQL、既有用户/会话/CSRF和资料完整度检查。论坛动态页面不走永久 `renderOnce` 缓存，私有数据不使用共享缓存。业务新增：

- 内容：主题、回复、编辑版本、幂等请求。
- 关系：关注关系，唯一 `(follower_id, followed_id)`，禁止自关注。
- 投票：主帖投票与回复投票各自建立唯一 `(target_id,user_id)`，`value` 为 1/-1，取消时删除；公开数字与自身状态分开返回。
- 收藏：用户与主题唯一关联。
- 消息：收件人、事件/聚合唯一键、目标、已读时间；每次读取重新检查目标权限和可见性。
- 举报与审计：举报原因、状态、处理人、理由与版本，操作历史只追加。
- 用户扩展：维护角色、禁言状态等字段通过显式迁移增加，个人资料接口不能更新这些字段。

关注列表、内容列表、消息、举报一律分页。所有写操作重新校验会话、资料、目标与权限。同连接事务内完成回复计数、投票变化和对应通知，重复请求不双计数。针对 `none→up→down→none`、重复关注和举报结案增加并发测试。投票统计首期可按真实投票记录聚合，避免仅修改无依据的计数。

## 六、验收按业务线进行

用 A、B、C 三个测试账号走完：

1. A 发布主题，B 从分类/搜索进入、回复，A 收到消息并定位回复。
2. B 关注 A，在关注页看到 A 的新主题；取消后不再出现，刷新状态正确。
3. B 对 A 主帖/回复分别执行赞、改踩、取消；同时操作不双计数，A 无法看到踩的人。
4. B 收藏后能从个人中心找到；取消后移除；目标隐藏不泄露内容。
5. C 举报 B 的回复，维护者通过受控命令处理，C 能看到结案理由，B 收到内容处理结果。
6. 举报被驳回、被举报内容先撤回、处理命令重复执行，工单均可正确结束且审计不丢失。
7. 用户只能查看自己的消息/收藏/举报，不能修改他人的内容或角色。
8. 登录回跳、失败草稿、重复提交、服务重启、数据库故障、手机版布局均完成验证。

实现可以依次做内容→关注与投票→消息与举报，但这些都属于同一个公开版本的验收范围，不能把未完成部分视作可无条件上线。

## 七、参考来源与适配

- [GitHub 关注用户](https://docs.github.com/en/get-started/exploring-projects-on-github/following-people)：借鉴关系与活动发现的联系；NanoCamp 采用“关注作者的新主题”这一明确范围。
- [GitHub Discussions](https://github.com/orgs/community/discussions)：借鉴分类列表和独立的发布入口。
- [Stack Overflow 踩的说明](https://stackoverflow.com/help/privileges/vote-down)：区分内容质量评价与需要处置的举报；不照搬其声望门槛、扣分或排序规则。
- [Discourse 举报机制](https://meta.discourse.org/t/flagging-a-post-for-moderator-attention/32783)：借鉴举报后的处理与反馈；不照搬自动隐藏规则。
- [CSDN](https://www.csdn.net/)：参考标题/摘要列表和作者信息区域，保留 NanoCamp 原有风格。

本轮先确认业务线与页面职责。上一版详情右侧发起讨论的原型作废；后续原型需新增作者关注、赞踩工具栏、消息和举报结果状态，不能沿用旧图作为开发合同。
